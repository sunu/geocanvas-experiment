# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, etc.) working in this repository. Humans are welcome to read it too.

## Project overview

**humanitarian-ttx** is a Humanitarian Table Top Exercise (TTX) for data exploration and response, built by Development Seed. The project is based on IFRC's Montandon project for data https://montandondata.org/. It's multiplayer canvas where users work on different aspects to developing a situation report after an event. It inludes finding related past events, current datasets, map visualizations, analysis ingests, etc.

At a high-level:
1. Users can start a new board and select an event from Montandon. This will do initial board setup. Showing the event data, map, and related events in that geography.
2. There are widgets for data selectors, map, charts, sticky notes, on our own infinite canvas.
3. There are agents running entirely in the browser to do specific actions. Create new components, run analysis etc.
4. Data comes from Montandon via Duckdb. Additional data like OSM, Overture (buildings/infra) comes as geoparquet too.
5. There's a way to ingest analysis run from Jupyternotebooks from a different project called Notebook Factory
6. There are programmable actions and flow control in the advanced mode
7. It is possible to create reports and export them


## Shared working agreement

This file is the source of truth for repository-wide agent guidance. `CLAUDE.md` imports it; keep shared rules here.

- Contributors may use different editors, agents, and development methods. Agree on behavior, scope, and verification; leave personal workflow choices to the contributor unless the task specifies one.
- Follow repository configuration and documented decisions, then the conventions in the code being changed. Keep personal preferences out of unrelated code and shared tooling.
- Read `README.md` for setup and layout, and package scripts for available checks. Consult relevant plans and decisions for the task; distinguish planned work from implemented behavior.
- Read `agent-docs/prd.md` before feature work: the product requirements, the rules every feature follows, and each feature's status (built, planned, not sequenced, stretch, out). `agent-docs/features.md` is the agreed scope, `agent-docs/architect.md` the architecture decisions, and `agent-docs/tasks/*` how a feature is built. Where those design docs differ from the code, the code and the PRD win.
- Update this file when a change introduces a shared workflow requirement that cannot be discovered from configuration. Keep machine-specific setup and personal agent instructions out of it.

- **Our own canvas, no tldraw.** tldraw needs a paid license off localhost, and the canvas we need is small. The design follows vsticky: a DOM "world" layer moved by one CSS transform. The camera is local to each person and never synced.
- **The board is a Yjs doc** (`packages/core/src/doc/board.ts`): one map of objects (box, text, sticky, map, event, notebook, reliefweb, country, presence, conflict, image, pdf), each a Y.Map of plain fields. Layer order is a float `z` per object, ties broken by id. The object type sets where a new object goes (`layer`): texts, sticky notes, events and notebooks on top, boxes and maps at the bottom, since they are mostly backgrounds. Text is stored as plain strings, with no encryption. The doc also has an `oplog` array (see ops below), and the `chat` and `uploads` arrays.
- **Ops are the only write path** (`plans/plan-007.md`). The UI, the palette and agents do not write the doc. They dispatch an op on the `Runtime` (`packages/core/src/ops/runtime.ts`). An op has a zod `args` schema, an optional read-only `prepare`, and a sync `apply` that writes through `BoardTx` in one transaction. `BoardTx` checks every add and update against the object type's schema. Use `runtime.dispatch` (sync) for gestures and typing, and `runtime.invoke` (async) for the palette and tools. Undo and redo cover only your own edits, one step per gesture: call `runtime.beginGesture()` when a gesture starts (a press, a key, a button). An op with `gesture: true` (drag, typing) writes one op log entry per gesture, not one per frame. If `apply` throws after a write, that write stays (Yjs has no rollback), so check input before the first write.
- **Plugins** add object types and ops (`definePlugin`). Each object type gets a `<type>.add` op. Core uses the same API (`packages/core/src/plugins/core.ts`). To add a type: write a headless plugin in `packages/plugins` (zod fields, ops) and list it there, then add its UI with `registerObjectUI` (view, tool, edit behavior) and, for special form fields, `registerWidget`, imported from `apps/web/src/plugins.ts`. Never change a stored type name or field: old boards use them.
- **Tools for an LLM:** `exportTools(runtime.availableOps(target))` gives JSON Schema tool definitions with input `{ ids, args }`. `runtime.callTool(name, input, actor)` runs one. Hidden ops are not tools, and an op with `risk: 'high'` runs only for a user actor. `summarizeBoard` gives an LLM a short text of the board. In dev, `window.runtime` is in the console.
- **The board agent** (`plans/plan-008.md`) runs in each room's Durable Object, as a headless `Runtime` with the actor `{ kind: 'agent' }` on the doc the room holds. Its code (`Agent`, the tool loop `runTurn`, the model client `chatCompletions`) is in `packages/plugins/src/agent/`, so a browser runs the same agent (see Bring your own key). People talk to it in the chat sidebar. The chat is a `chat` array in the board doc, one shared thread per board (`packages/core/src/chat.ts`). Each message stores the ids its sender had selected, and the agent acts on those ids, never on a live selection. The request also gives the last 10 chat entries of the hour before it, with the ids each message selected and each reply changed and added, so "the duplicate" can name an object that is not selected. The agent answers one message at a time with a plain tool loop on OpenRouter (`AGENT_MODEL` in `wrangler.jsonc`), at most 12 model calls per turn and 20 turns per room per hour. The agent may not add an object larger than 4× its type's default size (low-cost models sometimes send junk sizes such as `h: 4000`); the model is told to leave out `w` and `h`. Each reply stores what undoing it needs; its Undo button runs the hidden op `agent.undoTurn`, which refuses when someone changed those objects since. The size limit, placement and undo bookkeeping are in `callOp` (`packages/plugins/src/agent/call.ts`), which the MCP executor uses too. Read-only agent tools are not ops but ToolDefs (see Tools), in one `ToolRunner` per room, exported with `exportToolDefs` (input: the tool's own input): `board__get`; `data__geocode` and `data__reverseGeocode` (the browser's geocoding tools, on OpenCage with `OPENCAGE_API_KEY`, called directly), which the agent uses before `map.showArea`; and `events__search` (Montandon, when `MONTANDON_TOKEN` is set), which it uses before `event.add`. A tool whose key is not set is left out. The agent adds data layers to maps with `map.addLayer` and `map.pinPlace`. **Skills and deferred tools** (`plans/plan-020.md`): the domain rules (events, places on maps, map data, openEO) are skills, Markdown files in `packages/plugins/src/skills/` with frontmatter (`name`, `description`, `when_to_use`, `requires`, `optional`), imported as text (a Wrangler `Text` rule; `mdText` in the Vite and Vitest configurations). The system prompt lists only the skills whose `requires` tools the agent has; `skills__read` gives a body and loads its tools. Each call carries only the core ops, the `<type>.add` ops, `board__get`, `skills__read` and `tools__search` (keyword search, which loads the tools it finds); a deferred tool that the model names correctly still runs. To add a skill, write its file and import it in `skills/index.ts`; a new rule for the agent goes in a skill, not in `SYSTEM`, unless every request needs it. Each message also stores the center of the sender's view (`ViewController.center`): an add without `x` and `y` goes in the middle of it, as from the palette, and each further add in the same turn goes to the right of the last one. Then every agent add, with or without `x` and `y`, is kept off the objects already there (`freeSpot` in `call.ts`), since models often send the view center as `x` and `y` for every add and a new turn starts in the middle again: if it would come within `GAP` (24) of another object, it goes to the nearest free spot to the right on its row (past what is in the way, at most 4 of its own widths), else the same on the rows below, and after 10 rows below everything. Frames are not in the way, as things are meant to go in them (but a new frame does not go on another), and a frame given `x` and `y` stays there, around what it holds; templates keep their own placement. The request gives the agent the asker's person id and what they see on each map. The agent runs each tool call as `{ kind: 'agent', onBehalfOf: <asker's person id> }`, so ops that act on "my" things act on the asker's (`map.showArea` without `for` changes the asker's view), and the op log shows whom each agent write was for. Without `OPENROUTER_API_KEY`, the agent answers that it is not configured. The Durable Object also sets the agent's presence while it works; its awareness origin is then `'local'`, not a socket. That presence also says what the agent does now (`activity`: `Thinking` before each model call, a tool's title before each tool call; `onActivity` on `Agent` and `runTurn`) and whom it works for (`for`), one awareness update per step; browsers show it on the agent's cursor and in the chat's thinking line. A reply lists only the calls that failed: the rest shows on the canvas.
- **Bring your own key** (`plans/plan-009.md`): the chat panel's "My key" mode sends each message to an `Agent` in the sender's tab (`apps/web/src/agent/browserAgent.ts`), on the person's OpenRouter or OpenAI-compatible key. The key is in localStorage (`agent/keys.ts`) and goes only to the provider: never to the Worker, the doc, the chat or presence. A `UserMessage` with `browserTab` (a random id per page load) is answered only by that tab; one without it, by the room agent (`accepts` on `Agent`; `forRoom`). The browser agent has its own runtime with the actor `AGENT`, so its writes stay out of the person's ⌘Z; it sets `status: 'thinking'` and its `activity` on the person's presence and has no turn limit. Its tools are the room agent's, through the Worker's proxies. The provider must allow CORS (OpenRouter and OpenAI do; Ollama needs `OLLAMA_ORIGINS`). Next step (planned, not built): only internal users' sockets may use the room agent.
- **External agents through MCP** (`plans/plan-010.md`, local only): `npm run mcp` starts the companion (`apps/mcp/`) on `127.0.0.1:8790`, with Streamable HTTP at `/mcp`; `apps/mcp/src/stdio.ts` is the stdio entry for clients that start a command. The companion runs no model and holds no board. It routes each call to the browser tab that shows the board, where `apps/web/src/mcp/executor.ts` runs it on its own `Runtime` (actor id `mcp`, `onBehalfOf` the tab's person). Its tools are the tab's manifest: every op that is not hidden or high-risk and the browser's read-only tools, each with a `board` (the board link), so a new op or tool needs no companion change. A tab connects only on a local host and after the person opens a link the companion gave (`#room=<id>&mcp=<port>:<token>`). The companion keeps its token in `~/.config/ttx-mcp/token` (delete it to unpair every browser); under `npm run dev` the dev server hands it to the app's own pages (`/__ttx-mcp`, same-origin only), so a tab pairs with no link.
- **Multiplayer runs on our own Cloudflare Worker.** `/connect/<room>` goes to that room's Durable Object, which speaks the standard y-websocket protocol, keeps the doc in memory and appends every update to its SQLite (compacted into one row when there are more than 500, on load and while the room runs). Cloudflare caps a SQLite row at 2 MB, so larger updates are split across rows (`apps/worker/src/updateLog.ts`). Websockets use Cloudflare's Hibernation API (`ctx.acceptWebSocket`): the room leaves memory between messages, so open but idle tabs cost no Durable Object time. With `socket.accept()` a room is billed for as long as any tab is connected, which used up the free plan's daily allowance (13,000 GB-s, reset at 00:00 UTC) and took every board offline. Presence (awareness) is kept in memory only: it starts empty after a wake and browsers re-send theirs every 15 s; which presence ids a socket controls is kept on the socket (`serializeAttachment`). Presence carries each person (`board/person.ts`: id, name and color; the name starts as a random animal, and the person changes it with the name button beside the connection light in the toolbar, which updates presence at once; older chat messages keep the name they were sent with), their cursor in world coordinates, their selected ids, and the agent's `status` (`board/presence.ts`); `canvas/Peers.tsx` draws others' cursors and selection outlines. Agents have a cursor too, but not in presence: each browser moves it to every object an agent adds or changes, from the shared op log (`canvas/agentCursor.ts`), so it costs no model tokens and wakes no room, and works the same for the room's agent, one on a person's own key and one through MCP. What an agent adds is drawn once its cursor gets there (only the drawing waits; the doc has it at once), and an agent working off-screen shows as a marker on the canvas edge that goes there when clicked. The cursor appears when someone asks, and stays while the agent's presence says it works: with nothing selected, at a placeholder card ("Thinking…", or what the agent does) where its first add will land (`firstAddSpot` in `call.ts`, the same rule as the agent's placement, for a neutral size), which grows into that add when it comes and fades if the agent does something else; with a selection, at the selected objects, which the agent most likely changes; the asker's camera follows it (`targetFor`) when what it works on goes out of view, at the same zoom, until they scroll, zoom or pan themselves, and their next request starts it again (others' cameras never move); its tag shows the presence's `activity`, except while it places objects, which say what it does. It stays at each object while that object is busy (at least 0.8 s, and while its data loads, at most 3 s) before it moves to the next, so it is seen placing each one and a burst of calls does not rush past slow widgets; it hovers all the time (a slow drift of a few pixels on top of its moves). An object the agent worked on is busy for a moment and for as long as its data is loading in that browser: a placeholder card over it in the agent's violet (dashed edge, a light sweeping across, a ring and what the agent does: "Generating map…" for an add, else the op's title), with the cursor at its bottom-right corner: views report loading with `useReportLoading` (`canvas/loading.ts`, local, never synced). Cursor updates are capped at 10 per second, since each one wakes the room. The browser uses y-websocket's `WebsocketProvider`. Tabs of one browser also sync with each other directly (BroadcastChannel), so test multiplayer from two origins or two browsers, or the server is not involved.
- **Input:** drag on empty canvas to select; shift+drag selects from anywhere, even over a map or box, and adds to the selection; shift+click toggles one object; scroll pans; pinch or ⌘+scroll zooms; space+drag pans. Tools: V select, R rectangle (the box, with L line, ⇧L arrow and O ellipse as its other shapes), T text, S sticky note, M map, E event, N notebook, I image (each object type's UI registers its tool). Drop an image or a PDF anywhere on the board to upload it and place it there (`uploads/drop.ts`); an image object takes a picture dropped on it. Dragging files over the window dims it with a drop target; drops are handled on the window, so a drop on a panel does not make the browser open the file. Each file shows as a box with its upload progress where its object will go (`uploads/pending.ts`, local to the tab; uploads use XMLHttpRequest, the only way to see upload progress); a file that cannot be added keeps its box with the reason until dismissed. ⌘K opens the command palette. `]` / `[` bring to front / send to back, with ⌘ one step. Delete removes. Right click on an object opens its menu (duplicate, layer order, delete) on the selection (`canvas/ObjectMenu.tsx`); empty canvas has none. Double-click the name above a widget to rename it (an optional `name` on every object, set by `core.object.rename`; '' goes back to the widget's own). Double-click edits a text or sticky note, lets a map or a shown notebook take the pointer, or opens an event's search or a notebook's run picker; Esc gives it back. The left panel sets the color and text size of selected objects whose type has them (`defaultColor`, `textSize` in the type's definition; `canvas/style.ts`: colors are stored by name). A text's height follows its content; only the person who changed it refits it.
- **UI components: shadcn/ui on Tailwind v4, tokens from Figma.** The Figma file "Atlantis Pod Week Hack - AHD TTX" is the source of truth for the app's chrome (title bar, Ask panel, canvas toolbar, user menu): same spacing, radii (`--radius` 10px: md 8, lg 10, xl 14), Geist for all text. Components are in `apps/web/src/components/ui` (add more with `npx shadcn@latest add <name> -c apps/web`; the CLI writes `from "cn"` and lucide icons: change them to `@/lib/utils` and Phosphor), tokens in `apps/web/src/shadcn.css`. Tailwind's preflight is not loaded, since the app's own CSS is plain CSS written without it and a reset would change every canvas object: elements that use shadcn components carry the `ttx-ui` class (and portaled menus have it built in), which applies the part of the reset they need. Layer order is declared in `shadcn.css`; keep it first. New chrome is built with the components and Tailwind classes; the canvas objects and widgets stay on plain CSS until they are redesigned.
- **Where CSS goes.** Each feature keeps its plain CSS beside its code, one file per folder (`canvas/canvas.css`, `canvas/focus.css`, `map/map.css`, `reports/reports.css`, …), with classes prefixed by the feature (`.ttx-map__…`). `apps/web/src/styles/index.css` is the only place that loads them, in a fixed order: later files win where two rules of the same specificity meet (`map/map.css` comes after `canvas/focus.css`, since a map's location tools and layer list sit in the Options panel). A new feature adds its file there; never import a feature's CSS from a component, which would make the order depend on the module graph. Shared values are in `styles/tokens.css` (`--ttx-*`); `mobile/mobile.css` is the phone layout's, loaded with it.
- **Corners and elevation: chrome vs canvas.** The UI chrome (toolbar, panels, menus, dialogs, popovers: the objects built with the shadcn components) has rounded corners (`rounded-md` 8px for controls, `rounded-lg` 10px for bars and panels, never fully round pills or circles except status dots and avatars) and a small elevation shadow (`shadcn/Shadow/md`, as in the Figma toolbar). Elements on the canvas (boxes, text, sticky notes, maps, events, notebooks, images, PDFs and the like) always have square corners (`border-radius: 0`) and no elevation: no `box-shadow` or `drop-shadow`; they are separated by borders and fills only. Selection outlines and handles stay square and flat too.
- **Who is who on the canvas** (`plans/plan-011.md`): your own selection, handles and marquee are cyan (`--canvas-accent`), other people each have a color of their own, unique on the board (`apps/web/src/board/collaborators.ts`, solid outlines), and the agent is violet (`--agent`, dashed outlines, a sparkle). Never give a person cyan or violet, and do not use color alone to tell roles apart.
- **Icons:** Phosphor (`@phosphor-icons/react`, regular weight, imported as `<Name>Icon`; only imported icons are bundled). Icon-only buttons carry a `title` and an `aria-label`. For hazard and humanitarian-sector symbols, which Phosphor lacks (earthquake, volcano, displacement, clusters), consider the OCHA Humanitarian Icons; check their license first.
- **Focus mode** (`agent-docs/tasks/in-focus-widgets.md`; `canvas/Canvas.tsx`, `canvas/OptionsPanel.tsx`, `canvas/focus.ts`): a focusable type (`FocusableObjectUI` in `canvas/registry.ts`) fills the screen with its Options panel on the right. By default its edits go to a private `Draft` (`packages/core/src/ops/draft.ts`) until Share, and leaving with unshared changes asks Share, Discard or Keep editing. A type may set `live: true` to edit the board directly (no draft, Share or exit dialog), `keepChat: true` to keep the agent chat open as an overlay at the top left (the canvas gets `keeps-chat`, and `canvas/focus.css` shows `.ttx-chatpanel`; it takes no room), and `fullScreen: true` to fill the screen to its edges beside the Options panel (`focusArea(w, h, { full })`). Reports are all three. The canvas carries `data-focus` with the type in focus, for a type's own look of the whole view. The Options panel's header shows the object's title: its name, else its type's `panel(object, board)` title, else the type's. Esc leaves focus unless it was typed in a field (the chat, an Options input). Options get `onGoTo(id)` to leave focus and show another object.
- **Map widget** (`apps/web/src/map/`): a live MapLibre map in a box. The basemap is shared board state. **Map views are per person, in the doc:** the `views` map (person id → object id → center, zoom, bearing, `at`; `packages/core/src/views.ts`), so nobody's pan moves another person's map, but the agent can read and change a person's view, and one person can later follow another. A person's pans are written directly, 1 s after the map stops, with no op log entry and no undo. Ops change views through `BoardTx.setView`: `map.showArea` moves the views of given people, of everyone, or of the runner (for an agent: the person it acts for). A person with no view of a map starts at the latest view anyone saved. Deleting an object deletes its views. A person is one browser: the id, name and color are in localStorage (`board/person.ts`), so two tabs of one person share views; undo is still per tab, because each tab has its own runtime. "Go to place" in the header geocodes (`data.geocode`) and moves only your own view; its pin also marks the place for everyone, as a data layer. The Options panel's Location tools (`map/LocationPicker.tsx`) move everyone's view with `map.showArea` (`for: 'everyone'`), so in focus others see it once shared: drag a box on the map (`map/draw.ts`; Esc cancels), type `lat, lon` (about 20 km around it, `map/location.ts`), or describe the area in words, which goes to the agent through the board's chat (`agent/ask.ts`; shown only when `/agent/status` says an agent can geocode). A map still at the whole world shows "Choose a location", which opens focus.
- **Tools** (`packages/core/src/tools/`, design in `plans/plan-006.md` on `feat/tools-registry`): a tool is a typed, read-only, async capability (`defineTool`: zod input, an `output` kind such as `geo.features`, `run`). Tools never write the board; ops do. Each environment lists the tools it can run in one `ToolRunner`: the browser in `apps/web/src/tools/registry.ts` (geocoding through the Worker's proxy, and the data tools, which need browser APIs), the room's agent in `apps/worker/src/worker.ts`. The runner validates the input, caches results by (id, parsed input) in an LRU, shares concurrent calls, and does not keep failures. Why the cache: every person's map runs its layers' tools, and services are slow or rate limited (OpenCage's free tier: 1 request/s). A tool can call another through `ctx.tool`.
- **Map data layers**: a map's `layers` (an optional field of the map plugin, `packages/plugins/src/mapLayers.ts`) holds recipes (`{ id, tool, input, title }`), not data. They are written only through ops: `map.addLayer` (one of `DATA_LAYERS`, for an area), `map.pinPlace`, `map.addNotebookResult` (a notebook run's GeoJSON file, no area; in the notebooks plugin), `map.addEventLayer` (an event's footprint, no area; in the events plugin), `map.addBoundaries` and `map.addChoropleth` (COD-AB boundaries and HDX HAPI figures by area, below), `map.setLayerArea` and `map.removeLayer`, so the agent can add them and undo covers them. Each browser runs the tool and draws the result in the deck.gl overlay (`apps/web/src/map/layers.ts`), chosen by the tool's `output`: `geo.features` as a `GeoJsonLayer`, `geo.raster` (a COG url, value range and color ramp) with deck.gl-geotiff's `COGLayer` (`map/raster.ts`), below features. One failing layer does not stop the others; the layer list shows errors and a result's `attribution`. A layer that works on an area (a bbox [west, south, east, north]) gets the area when it is added: the UI passes the adder's live view, and without one the op uses the runner's saved view (for an agent: the asker's). So everyone sees the same data although views are per person; the layer list's crosshair resets it to your view, for everyone. `layers` is replaced as a whole, so two people adding a layer at the same moment keep only one.

- **Flood depth and damage** (`plans/plan-016.md`, `apps/web/src/inundation/`): the Exposure section's "Flood depth" picks a river flood of a return period (`scenario.exposure.returnPeriod`, one of `RETURN_PERIODS`: 10 to 500 years, through `map.setExposure`). Montandon's flood items have no depth (GDACS and PDC give scores, CEMS outlines and an extent), so depth comes from the JRC / CEMS GloFAS global river flood hazard maps (v2.1.2, 90 m, metres of water): 271 tiles of 10° of GeoTIFF (float32, deflate, 256 px internal tiles, no overviews), read by range through the Worker (`/floodmaps/*`, `apps/worker/src/floodmaps.ts`: the JRC server sends no CORS headers; GET only, the tile index and depth tiles only) with our own reader (`inundation/glofas.ts`: the header, then only the internal tiles asked, decompressed with `DecompressionStream`; no dependency). GloFAS reports depths over 10 m in some small channels (its `Spurious_Depths` mask marks them; not applied yet): Nepal's 100-year flood puts 138 of 3,575 flooded buildings there. Measured on Nepal's flood footprint (GDACS and CEMS areas): 3 s for depth and damage once the buildings are read.

- **Weather forecast layers** (`packages/plugins/src/weather.ts`, design and terms in `agent-docs/tasks/weather-forecast.md`): rain (total mm) or peak 10 m wind over the next 24, 48, 72 or 120 hours, from NOAA's GFS on dynamical.org, as a map layer (`map.addForecast`, a map's Options panel). Forecast context for planners, not a warning or impact estimate: the layer's caption says so and the map's credits show it. dynamical.org serves chunked arrays in an Icechunk repository on public S3 (CC BY 4.0, CORS open), not an API, so `IcechunkGfs` reads only the cells of the area, by range request, with `icechunk-js` and `zarrita` (loaded on the first read). **Workers cannot compile WebAssembly from bytes, which zarrita's Blosc codec (numcodecs) does**, so the room's agent failed to add forecasts (`Wasm code generation disallowed by embedder`) while browsers worked: `packages/plugins/src/blosc.ts` is a pure-JS replacement (with `fzstd`) registered in zarrita's codec registry, for the one frame type dynamical.org writes (zstd, byte shuffle, flag 0x91; anything else throws). Test anything that reads data from a Worker in a Worker (`wrangler dev`), not only in Node or a browser. The tool `weather.forecast` returns a `geo.grid` (a small grid, 0.25°), which `map/grid.ts` colors on the CPU and draws as one deck.gl `BitmapLayer`, cells unsmoothed. **The layer's recipe stores the forecast run** (`run`, an ISO time): `map.addForecast` looks up the newest run with data for the whole horizon when the layer is added (the repository does not say how far a run got, so it reads one cell at the last step, newest run first, up to 4 runs back), so everyone sees the same forecast and the title names it. The op's `prepare` is async: call it with `runtime.invoke`, not `dispatch`. An area is at most 30° by 30°; a wider one fails with "zoom in" before anything is read. Rain is the sum of GFS's average rate (kg m-2 s-1 = mm/s) times each step's length; a cell missing any step is empty, never a smaller total. Latitudes must run north to south, or the tool fails instead of drawing upside down. Cold, a layer takes about 10 s. Not built: a point forecast or time series (waits for the Chart widget), a hover value, other variables or models (the repository has temperature, pressure, GEFS and ECMWF IFS/AIFS), a refresh to a newer run. All three share a frame (`hapi/CountryWidget.tsx`: header, country picker on double-click, a `source` link per part) and the op `country.setCountry`. *Who's where* (`presence`, `hapi/presence.ts`) counts the organizations of the current year's 3W (`operational-presence`) by province, with the sectors as a filter that is shared on the board (`sector` field, `presence.setSector`; `''` is all sectors, since an update cannot clear a field) and the organizations in the most provinces; mostly countries with a response plan have a 3W. *Conflict* (`conflict`, `hapi/conflict.ts`) shows ACLED's political violence events and fatalities for the current month and the 11 before it, by month and the provinces with the most events. Some countries have national totals only (e.g. Nepal). HAPI marks districts it could not match to a P-code with codes like `MZ01-XXX`, and their province can be wrong (in October 2026 Mozambique's Quissanga was under Niassa and Nampula's districts under Sofala): they count in the totals but not in a province. Larger answers are read page by page (`hapiAll` in `hapi/api.ts`): HAPI stops at 10,000 rows without saying so.

HDX HAPI's areas come from the same CODs, so its rows join to the tiles by P-code (checked for Mozambique). A map's "Add layer" menu offers the figures of the who's where and conflict widgets on the board, and fits the adder's view to the country with the geocoder. - **Uploads** (`packages/core/src/uploads.ts`, `apps/worker/src/uploads.ts`): files people upload to a board, in R2. `POST /uploads?room=<room>&name=<file name>` with the file as the body goes to that room's Durable Object, which stores it and appends an entry (id, `kind`, name, type, size, uploader, time) to the doc's `uploads` array, so the list syncs like any edit. ### Adding an object type

A type is a headless definition plus its UI. The canvas, toolbar, side panel, palette and agent read everything from the registries, so a new type needs no changes elsewhere.

1. In a plugin in `packages/plugins` (`definePlugin`), add an `ObjectTypeDef`: zod `fields`, `defaultSize`, `layer` (`top` for content, `bottom` for backgrounds), `summarize` for the agent, and `defaultColor` and `textSize` if the side panel can set them. It gets a `<type>.add` op. A field added later, when objects of that type already exist on boards, must be optional, with a default where it is read. Never change a stored type name or field.
2. In the web app, call `registerObjectUI` (`canvas/registry.ts`): a `View`, a `tool` (key, label, Phosphor icon), and the behaviour it needs: `editable` (double-click), `editOnCreate`, `widthOnly`, `isEmpty` (removed when left empty). Import the file from `apps/web/src/plugins.ts`; the order of registration is the toolbar order.
3. Write through ops only. Store references to data (an event id, a tool recipe), not the data itself: each browser fetches what it shows.

Older tabs show a placeholder for a type they do not know, so a board stays usable while people reload after a deploy.

The first prototype is on the `experiment` branch: a headless op runtime, typed data links, a disasters plugin on Montandon, and a natural-language command pipeline. It is a reference, not a base. Read it before rebuilding a part it covered, in particular:
- `apps/web/src/nodes/MapView.tsx` and `plans/plan-005.md`: maps inside a canvas (edit and focus modes, WebGL context limits, pixel ratio at canvas zoom).
- `packages/plugin-disasters/src/montyProvider.ts`: the Montandon queries that `packages/plugins/src/monty/client.ts` has not taken over yet: related events near an event and impact tables.
- `feat/tools-registry` (`plans/plan-006.md`): the measured sizes and timings behind the data tools, and the admin boundary sources that were tried and dropped (COD-AB, Overture divisions, geoBoundaries).

## Deploys

GitHub Actions deploy every push to Cloudflare (`.github/workflows/deploy.yml`), after typecheck and tests pass:
- `main` deploys to the `humanitarian-ttx` Worker.
- Every other branch deploys to its own Worker, `humanitarian-ttx-<branch>` (naming rule in `.github/scripts/worker-name.sh`), with its own rooms. A branch that changes the board format cannot break `main`'s boards.
- Deleting a branch deletes its Worker and its rooms (`delete-branch-worker.yml`).
- The deployed URL is in each run's summary, and on the branch's pull request as one comment that each deploy updates (`.github/scripts/pr-preview-comment.sh`). A pull request opened after the branch deployed gets the link from `pr-preview-link.yml`.

Repository secrets: `CLOUDFLARE_API_TOKEN` (a token limited to editing Workers and R2, which deploys need to make each Worker's uploads bucket; R2 must be enabled on the account), `CLOUDFLARE_ACCOUNT_ID`, `MONTANDON_TOKEN`, `OPENROUTER_API_KEY`, `OPENCAGE_API_KEY` and `HAPI_APP_IDENTIFIER`. Cloudflare keeps secrets per Worker and each branch is its own Worker, so the workflow uploads the API keys the repository has with every deploy (`--secrets-file`). A missing key does not fail the deploy: event search, place search and country context answer 503, and the agent answers that it is not configured.

## Before editing

- Identify the requested outcome and how to verify it. For substantial or ambiguous work, state the scope and assumptions before implementing. Ask when uncertainty would change behavior or a shared contract; resolve routine implementation choices using existing conventions.
- Inspect the working tree and relevant code, tests, and callers. Search for an existing implementation before generating a new one.
- Treat existing uncommitted changes as another contributor's work. Preserve them, stage only your own changes, and ask before overwriting overlapping work. Re-read files before editing if they may have changed during the task.
- Keep independent tasks on separate branches or worktrees. Coordinate overlapping changes to shared interfaces, configuration, and lockfiles; do not silently broaden the task to accommodate another task's work.

## During code generation

Apply these rules while choosing an implementation and again when reviewing the diff:

- **YAGNI:** Implement the current requirement and its necessary correctness safeguards. Every new option, dependency, abstraction, and fallback must serve that requirement or an established contract. Defer speculative extension points, unused helpers, and features for hypothetical future callers.
- **DRY:** Keep each business rule and invariant in one authoritative place. Reuse existing code when its semantics match. Extract shared code when callers represent the same concept and should change together; similar syntax alone is not enough. Small duplication is preferable to coupling unrelated behavior through a configurable abstraction.
- **Simplicity:** Choose the smallest clear design that satisfies the requirement. Prefer explicit control flow and existing building blocks. Add indirection only when it reduces demonstrated complexity; avoid broad cleanup, renaming, or formatting outside the task.
- **Compatibility:** Inspect affected callers before changing shared interfaces or data formats. Preserve established behavior outside the requested change, and document intentional compatibility changes and any migration needed.
- **Maintainability:** Use names and boundaries that make intent clear to the next contributor. Comments should explain constraints or reasoning that the code cannot express. Record consequential shared design decisions in the repository rather than leaving them only in chat.
- New frameworks or dependencies require a plan, ADR, or ticket as well as the human approval described below.

## Verification and handoff

- Verify observable behavior against the requested outcome. Add or update tests for changed behavior and bug regressions; choose the test level that catches the failure without binding the test to implementation details. Test-first and implementation-first workflows are both acceptable.
- Run the relevant available tests, type checks, and linters before requesting review. For documentation-only changes, check accuracy, links, and the diff. Report checks that failed or could not run, including known pre-existing failures; never imply an unrun check passed.
- Review the final diff for scope, accidental changes, unnecessary abstractions, and duplicated rules. Account for every changed file before handing off.
- Summarize the resulting behavior, why it changed, verification performed, and any remaining limitations or follow-up work. Give reviewers enough context without requiring access to the agent conversation.

## Git and PRs

- Start new work from `main` on a task branch; continue an existing task on its branch. Integrate through a reviewed PR, subject to the publishing approval below; never push directly to `main`.
- Keep each PR focused on one coherent change. Separate unrelated cleanup so other contributors can review, merge, and revert changes independently.
- Write clear commit messages describing *why*, not just *what*.
- Resolve conflicts by preserving the intent of both changes and rerun affected checks. Ask when those intents conflict instead of choosing one contributor's version by default.

## Ask before

Agents should check with a human before:

- Adding or upgrading dependencies
- Changing scenario content or exercise logic in ways facilitators rely on
- Deleting files, rewriting history, or force-pushing
- Anything that publishes or sends data outside the repo
