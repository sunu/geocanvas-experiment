# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, etc.) working in this repository. Humans are welcome to read it too.

## Project overview

**humanitarian-ttx** is a Humanitarian Table Top Exercise (TTX) for data exploration and response, built by Development Seed. The project is based on IFRC's Montandon project for data https://montandondata.org/. It's multiplayer canvas where users work on different aspects to developing a situation report after an event. It inludes finding related past events, current datasets, map visualizations, analysis ingests, etc.

At a high-level:
1. Users can start a new board and select an event from Montandon. This will do initial board setup. Showing the event data, map, and related events in that geography.
2. There are widgets for data selectors, map, charts, sticky notes, on our own infinite canvas.
3. There are agents running entirely in the browser to do specific actions. Create new components, run analysis etc.
4. Data comes from Montandon via Duckdb. Additional data like OSM, Overture (buildings/infra) comes as geoparquet too.
5. There's a way to ingest analysis run from Jupyternotebooks from a different project called Notebook Factory
6. There are programmable actions and flow control in the advanced mode
7. It is possible to create reports and export them


## Shared working agreement

This file is the source of truth for repository-wide agent guidance. `CLAUDE.md` imports it; keep shared rules here.

- Contributors may use different editors, agents, and development methods. Agree on behavior, scope, and verification; leave personal workflow choices to the contributor unless the task specifies one.
- Follow repository configuration and documented decisions, then the conventions in the code being changed. Keep personal preferences out of unrelated code and shared tooling.
- Read `README.md` for setup and layout, and package scripts for available checks. Consult relevant plans and decisions for the task; distinguish planned work from implemented behavior.
- Read `agent-docs/prd.md` before feature work: the product requirements, the rules every feature follows, and each feature's status (built, planned, not sequenced, stretch, out). `agent-docs/features.md` is the agreed scope, `agent-docs/architect.md` the architecture decisions, and `agent-docs/tasks/*` how a feature is built. Where those design docs differ from the code, the code and the PRD win.
- Update this file when a change introduces a shared workflow requirement that cannot be discovered from configuration. Keep machine-specific setup and personal agent instructions out of it.

## Repository layout

npm workspaces monorepo (TypeScript, ESM). Design docs go in `plans/`; product requirements and task specs in `agent-docs/` (start with `agent-docs/prd.md`).

```

                 agent's own (board.get, events.search); the board's agent (src/agent/: Agent, its tool loop and
```

- **Our own canvas, no tldraw.** tldraw needs a paid license off localhost, and the canvas we need is small. The design follows vsticky: a DOM "world" layer moved by one CSS transform. The camera is local to each person and never synced.
- **The board is a Yjs doc** (`packages/core/src/doc/board.ts`): one map of objects (box, text, sticky, map, event, notebook, reliefweb, country, presence, conflict, image, pdf), each a Y.Map of plain fields. Layer order is a float `z` per object, ties broken by id. The object type sets where a new object goes (`layer`): texts, sticky notes, events and notebooks on top, boxes and maps at the bottom, since they are mostly backgrounds. Text is stored as plain strings, with no encryption. The doc also has an `oplog` array (see ops below), and the `chat` and `uploads` arrays.
- **Ops are the only write path** (`plans/plan-007.md`). The UI, the palette and agents do not write the doc. They dispatch an op on the `Runtime` (`packages/core/src/ops/runtime.ts`). An op has a zod `args` schema, an optional read-only `prepare`, and a sync `apply` that writes through `BoardTx` in one transaction. `BoardTx` checks every add and update against the object type's schema. Use `runtime.dispatch` (sync) for gestures and typing, and `runtime.invoke` (async) for the palette and tools. Undo and redo cover only your own edits, one step per gesture: call `runtime.beginGesture()` when a gesture starts (a press, a key, a button). An op with `gesture: true` (drag, typing) writes one op log entry per gesture, not one per frame. If `apply` throws after a write, that write stays (Yjs has no rollback), so check input before the first write.
- **Plugins** add object types and ops (`definePlugin`). Each object type gets a `<type>.add` op. Core uses the same API (`packages/core/src/plugins/core.ts`). To add a type: write a headless plugin in `packages/plugins` (zod fields, ops) and list it there, then add its UI with `registerObjectUI` (view, tool, edit behavior) and, for special form fields, `registerWidget`, imported from `apps/web/src/plugins.ts`. Never change a stored type name or field: old boards use them.
- **Tools for an LLM:** `exportTools(runtime.availableOps(target))` gives JSON Schema tool definitions with input `{ ids, args }`. `runtime.callTool(name, input, actor)` runs one. Hidden ops are not tools, and an op with `risk: 'high'` runs only for a user actor. `summarizeBoard` gives an LLM a short text of the board. In dev, `window.runtime` is in the console.
- **The board agent** (`plans/plan-008.md`) runs in each room's Durable Object, as a headless `Runtime` with the actor `{ kind: 'agent' }` on the doc the room holds. Its code (`Agent`, the tool loop `runTurn`, the model client `chatCompletions`) is in `packages/plugins/src/agent/`, so a browser runs the same agent (see Bring your own key). People talk to it in the chat sidebar. The chat is a `chat` array in the board doc, one shared thread per board (`packages/core/src/chat.ts`). Each message stores the ids its sender had selected, and the agent acts on those ids, never on a live selection. The request also gives the last 10 chat entries of the hour before it, with the ids each message selected and each reply changed and added, so "the duplicate" can name an object that is not selected. The agent answers one message at a time with a plain tool loop on OpenRouter (`AGENT_MODEL` in `wrangler.jsonc`), at most 8 model calls per turn and 20 turns per room per hour. The agent may not add an object larger than 4× its type's default size (low-cost models sometimes send junk sizes such as `h: 4000`); the model is told to leave out `w` and `h`. Each reply stores what undoing it needs; its Undo button runs the hidden op `agent.undoTurn`, which refuses when someone changed those objects since. The size limit, placement and undo bookkeeping are in `callOp` (`packages/plugins/src/agent/call.ts`), which the MCP executor uses too. Read-only agent tools are not ops but ToolDefs (see Tools), in one `ToolRunner` per room, exported with `exportToolDefs` (input: the tool's own input): `board__get`; `data__geocode` and `data__reverseGeocode` (the browser's geocoding tools, on OpenCage with `OPENCAGE_API_KEY`, called directly), which the agent uses before `map.showArea`; and `events__search` (Montandon, when `MONTANDON_TOKEN` is set), which it uses before `event.add`. A tool whose key is not set is left out. The agent adds data layers to maps with `map.addLayer` and `map.pinPlace`. Each message also stores the center of the sender's view (`ViewController.center`): an add without `x` and `y` goes in the middle of it, as from the palette, and each further add in the same turn goes to the right of the last one. The request gives the agent the asker's person id and what they see on each map. The agent runs each tool call as `{ kind: 'agent', onBehalfOf: <asker's person id> }`, so ops that act on "my" things act on the asker's (`map.showArea` without `for` changes the asker's view), and the op log shows whom each agent write was for. Without `OPENROUTER_API_KEY`, the agent answers that it is not configured. The Durable Object also sets the agent's presence while it works; its awareness origin is then `'local'`, not a socket.
- **Bring your own key** (`plans/plan-009.md`): the chat panel's "My key" mode sends each message to an `Agent` in the sender's tab (`apps/web/src/agent/browserAgent.ts`), on the person's OpenRouter or OpenAI-compatible key. The key is in localStorage (`agent/keys.ts`) and goes only to the provider: never to the Worker, the doc, the chat or presence. A `UserMessage` with `browserTab` (a random id per page load) is answered only by that tab; one without it, by the room agent (`accepts` on `Agent`; `forRoom`). The browser agent has its own runtime with the actor `AGENT`, so its writes stay out of the person's ⌘Z; it sets `status: 'thinking'` on the person's presence and has no turn limit. Its tools are the room agent's, through the Worker's proxies. The provider must allow CORS (OpenRouter and OpenAI do; Ollama needs `OLLAMA_ORIGINS`). Next step (planned, not built): only internal users' sockets may use the room agent.
- **External agents through MCP** (`plans/plan-010.md`, local only): `npm run mcp` starts the companion (`apps/mcp/`) on `127.0.0.1:8790`, with Streamable HTTP at `/mcp`; `apps/mcp/src/stdio.ts` is the stdio entry for clients that start a command. The companion runs no model and holds no board. It routes each call to the browser tab that shows the board, where `apps/web/src/mcp/executor.ts` runs it on its own `Runtime` (actor id `mcp`, `onBehalfOf` the tab's person). Its tools are the tab's manifest: every op that is not hidden or high-risk and the browser's read-only tools, each with a `board` (the board link), so a new op or tool needs no companion change. A tab connects only on a local host and after the person opens a link the companion gave (`#room=<id>&mcp=<port>:<token>`). The companion keeps its token in `~/.config/ttx-mcp/token` (delete it to unpair every browser); under `npm run dev` the dev server hands it to the app's own pages (`/__ttx-mcp`, same-origin only), so a tab pairs with no link.
- **Multiplayer runs on our own Cloudflare Worker.** `/connect/<room>` goes to that room's Durable Object, which speaks the standard y-websocket protocol, keeps the doc in memory and appends every update to its SQLite (compacted into one row when there are more than 500, on load and while the room runs). Cloudflare caps a SQLite row at 2 MB, so larger updates are split across rows (`apps/worker/src/updateLog.ts`). Websockets use Cloudflare's Hibernation API (`ctx.acceptWebSocket`): the room leaves memory between messages, so open but idle tabs cost no Durable Object time. With `socket.accept()` a room is billed for as long as any tab is connected, which used up the free plan's daily allowance (13,000 GB-s, reset at 00:00 UTC) and took every board offline. Presence (awareness) is kept in memory only: it starts empty after a wake and browsers re-send theirs every 15 s; which presence ids a socket controls is kept on the socket (`serializeAttachment`). Presence carries each person (`board/person.ts`: id, name and color; the name starts as a random animal, and the person changes it with the name button beside the connection light in the toolbar, which updates presence at once; older chat messages keep the name they were sent with), their cursor in world coordinates, their selected ids, and the agent's `status` (`board/presence.ts`); `canvas/Peers.tsx` draws others' cursors and selection outlines. Cursor updates are capped at 10 per second, since each one wakes the room. The browser uses y-websocket's `WebsocketProvider`. Tabs of one browser also sync with each other directly (BroadcastChannel), so test multiplayer from two origins or two browsers, or the server is not involved.
- **Input:** drag on empty canvas to select; shift+drag selects from anywhere, even over a map or box, and adds to the selection; shift+click toggles one object; scroll pans; pinch or ⌘+scroll zooms; space+drag pans. Tools: V select, R box, T text, S sticky note, M map, E event, N notebook, I image (each object type's UI registers its tool). Drop an image or a PDF anywhere on the board to upload it and place it there (`uploads/drop.ts`); an image object takes a picture dropped on it. Dragging files over the window dims it with a drop target; drops are handled on the window, so a drop on a panel does not make the browser open the file. Each file shows as a box with its upload progress where its object will go (`uploads/pending.ts`, local to the tab; uploads use XMLHttpRequest, the only way to see upload progress); a file that cannot be added keeps its box with the reason until dismissed. ⌘K opens the command palette. `]` / `[` bring to front / send to back, with ⌘ one step. Delete removes. Double-click edits a text or sticky note, lets a map or a shown notebook take the pointer, or opens an event's search or a notebook's run picker; Esc gives it back. The left panel sets the color and text size of selected objects whose type has them (`defaultColor`, `textSize` in the type's definition; `canvas/style.ts`: colors are stored by name). A text's height follows its content; only the person who changed it refits it.
- **UI components: shadcn/ui on Tailwind v4, tokens from Figma.** The Figma file "Atlantis Pod Week Hack - AHD TTX" is the source of truth for the app's chrome (title bar, Ask panel, canvas toolbar, user menu): same spacing, radii (`--radius` 10px: md 8, lg 10, xl 14), Geist for all text. Components are in `apps/web/src/components/ui` (add more with `npx shadcn@latest add <name> -c apps/web`; the CLI writes `from "cn"` and lucide icons: change them to `@/lib/utils` and Phosphor), tokens in `apps/web/src/shadcn.css`. Tailwind's preflight is not loaded, since `styles.css` is plain CSS written without it and a reset would change every canvas object: elements that use shadcn components carry the `ttx-ui` class (and portaled menus have it built in), which applies the part of the reset they need. Layer order is declared in `shadcn.css`; keep it first. New chrome is built with the components and Tailwind classes; the canvas objects and widgets stay on `styles.css` until they are redesigned.
- **Corners and elevation: chrome vs canvas.** The UI chrome (toolbar, panels, menus, dialogs, popovers: the objects built with the shadcn components) has rounded corners (`rounded-md` 8px for controls, `rounded-lg` 10px for bars and panels, never fully round pills or circles except status dots and avatars) and a small elevation shadow (`shadcn/Shadow/md`, as in the Figma toolbar). Elements on the canvas (boxes, text, sticky notes, maps, events, notebooks, images, PDFs and the like) always have square corners (`border-radius: 0`) and no elevation: no `box-shadow` or `drop-shadow`; they are separated by borders and fills only. Selection outlines and handles stay square and flat too.
- **Who is who on the canvas** (`plans/plan-011.md`): your own selection, handles and marquee are cyan (`--canvas-accent`), other people each have one of six colors (`apps/web/src/board/collaborators.ts`, solid outlines), and the agent is violet (`--agent`, dashed outlines, a sparkle). Never give a person cyan or violet, and do not use color alone to tell roles apart.
- **Icons:** Phosphor (`@phosphor-icons/react`, regular weight, imported as `<Name>Icon`; only imported icons are bundled). Icon-only buttons carry a `title` and an `aria-label`. For hazard and humanitarian-sector symbols, which Phosphor lacks (earthquake, volcano, displacement, clusters), consider the OCHA Humanitarian Icons; check their license first.
- **Map widget** (`apps/web/src/map/`): a live MapLibre map in a box. The basemap is shared board state. **Map views are per person, in the doc:** the `views` map (person id → object id → center, zoom, bearing, `at`; `packages/core/src/views.ts`), so nobody's pan moves another person's map, but the agent can read and change a person's view, and one person can later follow another. A person's pans are written directly, 1 s after the map stops, with no op log entry and no undo. Ops change views through `BoardTx.setView`: `map.showArea` moves the views of given people, of everyone, or of the runner (for an agent: the person it acts for). A person with no view of a map starts at the latest view anyone saved. Deleting an object deletes its views. A person is one browser: the id, name and color are in localStorage (`board/person.ts`), so two tabs of one person share views; undo is still per tab, because each tab has its own runtime. "Go to place" in the header geocodes (`data.geocode`) and moves only your own view; its pin also marks the place for everyone, as a data layer. The Options panel's Location tools (`map/LocationPicker.tsx`) move everyone's view with `map.showArea` (`for: 'everyone'`), so in focus others see it once shared: drag a box on the map (`map/draw.ts`; Esc cancels), type `lat, lon` (about 20 km around it) or `west, south, east, north` (`map/location.ts`), or describe the area in words, which goes to the agent through the board's chat (`agent/ask.ts`; shown only when `/agent/status` says an agent can geocode). A map still at the whole world shows "Choose a location", which opens focus.
- **Tools** (`packages/core/src/tools/`, design in `plans/plan-006.md` on `feat/tools-registry`): a tool is a typed, read-only, async capability (`defineTool`: zod input, an `output` kind such as `geo.features`, `run`). Tools never write the board; ops do. Each environment lists the tools it can run in one `ToolRunner`: the browser in `apps/web/src/tools/registry.ts` (geocoding through the Worker's proxy, and the data tools, which need browser APIs), the room's agent in `apps/worker/src/worker.ts`. The runner validates the input, caches results by (id, parsed input) in an LRU, shares concurrent calls, and does not keep failures. Why the cache: every person's map runs its layers' tools, and services are slow or rate limited (OpenCage's free tier: 1 request/s). A tool can call another through `ctx.tool`.
- **Map data layers**: a map's `layers` (an optional field of the map plugin, `packages/plugins/src/mapLayers.ts`) holds recipes (`{ id, tool, input, title }`), not data. They are written only through ops: `map.addLayer` (one of `DATA_LAYERS`, for an area), `map.pinPlace`, `map.addNotebookResult` (a notebook run's GeoJSON file, no area; in the notebooks plugin), `map.addEventLayer` (an event's footprint, no area; in the events plugin), `map.addBoundaries` and `map.addChoropleth` (COD-AB boundaries and HDX HAPI figures by area, below), `map.setLayerArea` and `map.removeLayer`, so the agent can add them and undo covers them. Each browser runs the tool and draws the result in the deck.gl overlay (`apps/web/src/map/layers.ts`), chosen by the tool's `output`: `geo.features` as a `GeoJsonLayer`, `geo.raster` (a COG url, value range and color ramp) with deck.gl-geotiff's `COGLayer` (`map/raster.ts`), below features. One failing layer does not stop the others; the layer list shows errors and a result's `attribution`. A layer that works on an area (a bbox [west, south, east, north]) gets the area when it is added: the UI passes the adder's live view, and without one the op uses the runner's saved view (for an agent: the asker's). So everyone sees the same data although views are per person; the layer list's crosshair resets it to your view, for everyone. `layers` is replaced as a whole, so two people adding a layer at the same moment keep only one.
- **Map annotations**: what people mark on a map themselves, in its optional `annotations` field (`packages/plugins/src/mapAnnotations.ts`), each with a `kind` so markers and shapes can join later. Unlike data layers, they are the data, not a recipe. So far one kind: a **sticky note** pinned to a place (`lngLat`), with text. Ops `map.addSticky`, `map.setStickyText` (a gesture, like typing in a canvas sticky), `map.moveAnnotation` and `map.removeAnnotation`, so the agent can add one and undo covers them; `summarize` gives the agent each note's text and place. While a map is edited, its toolbar at the top right places one with the next click on the map (`MapObject.tsx`); drag a note to move it, double-click it to write, × removes it. Each note is a MapLibre `Marker` with a DOM element (`map/MapStickies.tsx`), not a deck.gl layer as `agent-docs/tasks/in-focus-widgets.md` planned: it stays on its place at the same size on screen, its text is sharp and editable, and it sits above the data layers. Writing ends with a press on the map outside the note, not on blur: React's development double mount puts the marker in the page again, which blurs its text box. `annotations` is replaced as a whole, like `layers`: two people typing in two notes of one map at the same moment can lose each other's last keystrokes. Notes are drawn only on live maps: a map that shows a snapshot (see Live maps and snapshots) does not show them.
- **Layers from a URL** (`map.addUrlLayer`, `URL_FORMATS` in `packages/plugins/src/mapLayers.ts`; the form is `map/UrlLayerForm.tsx`): GeoJSON, GeoParquet and zipped shapefiles (tool `data.urlFeatures`, read whole in a worker, `data/urlData.worker.ts`: hyparquet decodes GeoParquet's WKB, `shpjs` reads shapefiles and reprojects them with their `.prj`; at most 50 MB and 100,000 features, GeoParquet only in longitude/latitude), single-band COGs (`data.urlRaster`, checked with one range request, then the raster path below; the op takes the value range, default 0–100) and XYZ raster tiles (`data.urlTiles`, output `geo.tiles`, a deck.gl `TileLayer` under rasters and features). The format is guessed from the URL (`guessFormat`) or given. Every browser reads the URL itself, so the server must allow CORS; there is no proxy. The layer list shows a legend for each layer: the color in the shape of the features (dots, lines, areas) and their count, a raster's ramp and range, a choropleth's classes.
- **Layer filters and styles** (`map.setLayerFilter`, `map.setLayerStyle`; optional `filter` and `style` on each layer in `mapLayers.ts`): a filter (property, operator, value) and a color, a property to color by (quantile classes for numbers, as for choropleths, and the most frequent categories for text) and an opacity. They run in each browser on the features it loaded (`map/featureStyle.ts`), with no DuckDB; filter and color apply to features, opacity to every deck.gl layer. COD-AB boundaries and choropleths are MapLibre layers and are left out. The layer list's sliders button opens them, with the layer's attributes (name, type, a few values).
- **Live maps and snapshots** (`map/budget.ts`, `map/pool.ts`, `map/snapshots.ts`): each live map holds two WebGL contexts (MapLibre and the deck.gl overlay) and browsers keep about 16, so at most 4 maps are live (`LIVE_MAPS`), besides the edited and the focused one: those on screen and at least 200 × 140 px there, selected ones first, then the largest. The canvas publishes what the person sees (`canvas/viewport.ts`) and each map listens only to its own flag. The others show a PNG of the person's view, drawn one at a time by one hidden map (one MapLibre map with `preserveDrawingBuffer` and its deck.gl overlay: two more contexts for every snapshot in the tab), with the credits under it, since a picture has no attribution control; 50 are kept. A map that becomes live again starts from the doc's view. When a map's view changes doc (entering or leaving focus), it jumps to that doc's view first: after Discard the map still showed the draft's view, and the resize that ends focus saved it to the board.
- **Population** (`data/population.ts`): `data.population` reverse geocodes the area's center (rounded to 0.1°, so nearby areas reuse the cached answer) to find the country, then uses that country's WorldPop 2020 COG on Source Cooperative (public, CORS open, read by range request; never downloaded whole). An area across a border shows one country. `map/raster.ts` uploads each tile as a float texture and colors it in one shader step: nodata and values at or below the range minimum are not drawn, and the ramp uses the square root of the value so sparse areas stay visible. `vite build` needs `worker: { format: 'es' }` for the library's decoding worker.
- **Countries and buildings** read GeoParquet in the browser with hyparquet, each in its own Web Worker (`data/*.worker.ts`, started on the first query, so the main bundle does not grow). Pure helpers (`wkb.ts`, with the shared row-group selection, `worldBank.ts`, `overture.ts`, `layercake.ts`) are tested in Node; the workers only fetch and call them.
  - `data.adminBoundaries` (`data/boundaries.ts`): World Bank admin 0 on Source Cooperative (CC BY 4.0). The geometry column is one ~51 MB page, so the first query in a browser downloads it once (about 10 s) and keeps it in the Cache API; later page loads read ~0.5 MB and decode for about 4 s. Countries are matched by the bbox of each polygon part, so large neighbours appear. Admin 0 only.
  - `data.overture` (`data/buildings.ts`): Overture buildings, found through the Overture STAC catalog, reading only the row groups whose `bbox` statistics match (a Beira district: ~18 MB, ~7 s). The area must be at most 0.01 deg² (about 11 × 11 km), checked before any download; at most 100,000 buildings, then `truncated` and the layer list says so. ODbL attribution.
  - `data.healthFacilities` (`data/health.ts`): OpenStreetMap health facilities (`healthcare=*`, or `amenity` hospital, clinic, doctors, dentist, pharmacy) from Layercake's `pois` layer (OpenStreetMap US; one 4.7 GB planet file, spatially sorted, `bbox` statistics per row group, no page index). It reads only the small columns of the row groups that match, never `geometry` (~11 MB per row group), and puts each facility at the center of its `bbox`. Mozambique: 7 row groups, ~16 MB, ~7 s, 3,404 facilities; Beira: 1 row group, ~2 MB. More than 12 row groups fails before any download (a country works, a continent does not). The footer (~5 MB) is read once per page. Layercake answers `OPTIONS` with 403, so reads must be plain single-range GETs (CORS-safelisted, no preflight). ODbL attribution.
- **MapLibre 6.** It draws right-to-left labels (Arabic, Hebrew) itself, with no RTL plugin. It is ES modules only, and under Vite its worker must be imported as `maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url` and passed to `setWorkerUrl` (a plain `?url` import draws nothing in dev).
- **deck.gl runs in overlay mode** (`MapboxOverlay({ interleaved: false })`): deck.gl 9.4's interleaved mode throws on every frame with MapLibre 6. Overlay costs a second WebGL context per map, and deck.gl layers draw above the map's labels. deck.gl's canvas sits in MapLibre's top-left control container (z-index 2), so `.ttx-map__gl` isolates MapLibre's stacking; without it, data layers paint over the map's hint and layer list. Revisit interleaved mode when deck.gl supports MapLibre 6.
- **Event widget** (`apps/web/src/events/`): a disaster event from the Montandon STAC API. The board stores only `eventId`; each browser fetches the details (`apps/web/src/events/monty.ts`, one shared client with a cache). The client is in `packages/plugins/src/monty/`, so the agent can search too. Search text is read as country, hazard type, year and source (`search.ts`), turned into a CQL2 filter, and the leftover words rank by name. Hazard types use the UNDRR-ISC 2025 codes with their GLIDE and EM-DAT equivalents (`hazards.ts`; add a type only with its rows from the upstream table). Sources record one event under different `monty:corr_id`s, so an event's other sources are found by hazard, country and time, as upstream's correlation algorithm does. A map's "Add layer" menu lists the events on the board: `map.addEventLayer` adds a layer whose recipe names the event, and the browser tool `events.footprint` (`events/footprint.ts`, `MontyClient.getFootprint`) draws the hazard items of every source that reports it (GDACS and CEMS flood extents, EM-DAT affected areas, USGS earthquake areas, IBTrACS cyclone tracks) above the event points. Impact items are left out: they sit on the event's point. Points are not turned into made-up areas (the `experiment` prototype drew discs 80–300 km wide by hazard type), so an event whose sources give only points shows only points.
- **Notebook widget**: a published run of a [Notebook Factory](https://notebook-factory-staging.montandondata.org/api/) notebook (templates such as risk exposure or impact estimation, run for an area or a STAC item). The headless part is the `notebooks` plugin (`packages/plugins/src/notebooks.ts`): the `notebook` type stores the run id and a shared `view`, written by `notebook.setRun` and `notebook.setView`, and `map.addNotebookResult` adds a run's GeoJSON file to a map. The UI is in `apps/web/src/notebooks/` (`ui.tsx` registers the view, the N tool and the `notebookRun` form widget for the palette). The summary card shows the run's title, template, area, date, text and its published files (`artifacts`, e.g. CSV and GeoJSON) as links; the notebook view shows Notebook Factory's own rendered page (`output_url`) in a sandboxed iframe, so it looks as it does there and its interactive outputs work. The sandbox must include `allow-same-origin`: the page (a MyST site) loads its scripts as ES modules, which are fetched with CORS, and from a sandbox's opaque `null` origin every one was blocked. The page still cannot reach the board, which is a different origin. Double-click picks a run in the card, or lets the notebook take the pointer. It has in-focus mode (F or the header's button): the view fills the screen and has the pointer, and the Options panel (`notebooks/NotebookOptions.tsx`) switches the view, picks the run and lists the files, on the draft; "Show on a new map" is not offered in focus, since the map would go into the draft, hidden until shared. Notebook Factory sends no CORS headers, so the API is read through the Worker (`/notebooks/*`, `apps/worker/src/notebooks.ts`: GET only, runs, templates and published run files only, no secret: reading is anonymous); the iframe and file links need no CORS. The base URL is `NOTEBOOK_FACTORY_URL` in `wrangler.jsonc` (staging). A GeoJSON result layer's recipe names the run and file, not the url; the browser tool `notebooks.artifact` (`notebooks/artifact.ts`) reads it through `/notebooks/published/runs/<id>/outputs/…` and needs longitude/latitude (CRS84 or EPSG:4326). "Show on a new map" on the card adds a map beside the notebook with the layer (`map.add` with `layers`), and a map's "Add layer" menu lists the GeoJSON files of the notebooks on the board. The person who adds such a layer gets their view fitted to it (`fitMapTo` in `map/MapObject.tsx`): it writes their view in `views`, as their own pans are, and the map flies there. For a new map, the data is read before the map is added, so its view is written before the map appears; a view written just after a map appears is overwritten by the map's own first save (about 1 s after it mounts). Not built yet: a Notebook Factory search tool for the agent (it can add a result layer only for a run it is told about), runs for an event (a run's STAC item has `correlation_id` = `monty:corr_id`), CSV artifacts as tables, starting runs (needs a token).
- **ReliefWeb feed**: the latest [ReliefWeb](https://reliefweb.int) updates for an event's disaster (situation reports, maps, appeals, news): title, organisation, format, date, a short summary and the PDF, each linking to ReliefWeb. Added automatically beside an event when someone picks it and it has GLIDE numbers (`addFeedOnPick` in `events/EventObject.tsx`): only by the browser that picked, since every browser loads the event and each adding one would add one per person; not when the board already has a feed for the same GLIDE numbers (`feedFor`); and as its own undo step, about a second after the pick, once the event's details have loaded. Events the agent picks get none (its tools do not see GLIDE numbers). The card's "ReliefWeb updates" button adds one by hand, e.g. after a feed was deleted. There is no toolbar tool (`reliefweb.add` in the palette or for the agent). The `reliefweb` plugin (`packages/plugins/src/reliefweb.ts`) stores the disaster's GLIDE numbers (e.g. `FF-2026-000162-NPL`; op `reliefweb.setDisaster`), not the updates. ReliefWeb files disasters by GLIDE number, and Montandon has GLIDE records (`glide-event-<GLIDE>`), so `glidesOf(event)` reads an event's GLIDE numbers from the GLIDE records the event card's cross-source lookup finds; an event without one has no feed, and the button says so. The updates come from ReliefWeb's RSS (`https://reliefweb.int/updates/rss.xml?search=disaster.glide:"<GLIDE>" OR …`, the latest 20, newest first), which needs no key. ReliefWeb's API (v2) would allow paging and filtering but needs an approved `appname`, requested from ReliefWeb. The RSS sends no CORS headers, so the Worker reads it (`GET /reliefweb/updates?glide=…`, `apps/worker/src/reliefweb.ts`: GLIDE numbers only, the search is built there); the browser parses it (`apps/web/src/reliefweb/feed.ts`) and keeps it per page; the feed's refresh button asks again.
- **Country context**: a country's humanitarian figures from [HDX HAPI](https://hapi.humdata.org/docs), not tied to an event: INFORM risk and its dimensions, population, multidimensional poverty, people in need and targeted (all sectors, the latest plan), the latest round of each displacement operation IOM tracks (the 3 most recent), and the appeals of the latest two years with their funding. Each part links to its HDX dataset (`metadata/resource`), and a part that fails or has no data is left out (e.g. Nepal has no people in need: it has no response plan). Added from the palette (`country.add`, with a country picker widget) or by the agent; there is no toolbar tool. The `hapi` plugin (`packages/plugins/src/hapi.ts`) stores the ISO3 code (op `country.setCountry`), not the figures. The browser reads HAPI through the Worker (`/hapi/<theme>/<endpoint>`, `apps/worker/src/hapi.ts`: GET, data and metadata endpoints only) and picks the figures in `apps/web/src/hapi/context.ts`, once per country per page. HAPI needs an `app_identifier`, base64("app name:email"): not a key, but it carries the email, so the Worker adds it (`HAPI_APP_IDENTIFIER`) instead of every browser URL. HAPI allows about 60 requests a minute per identifier, shared by every board, and is refreshed daily, so the Worker lets browsers cache answers for an hour (the Cache API does not work on `workers.dev`). HAPI matches text filters as wildcards (`location_name=Mali` also gives Somalia): filter by code. Province and district figures as tables are not built yet.
- **Who's where and Conflict**: two more HDX HAPI widgets for one country, beside the country context, from HAPI's coordination & context endpoints (national risk and funding are on the country context). All three share a frame (`hapi/CountryWidget.tsx`: header, country picker on double-click, a `source` link per part) and the op `country.setCountry`. *Who's where* (`presence`, `hapi/presence.ts`) counts the organizations of the current year's 3W (`operational-presence`) by province, with the sectors as a filter that is shared on the board (`sector` field, `presence.setSector`; `''` is all sectors, since an update cannot clear a field) and the organizations in the most provinces; mostly countries with a response plan have a 3W. *Conflict* (`conflict`, `hapi/conflict.ts`) shows ACLED's political violence events and fatalities for the current month and the 11 before it, by month and the provinces with the most events. HAPI's ACLED event types overlap (`political_violence` includes `civilian_targeting`; `demonstration` is apart), so only `political_violence` is read, never a sum of the types. Some countries have national totals only (e.g. Nepal). HAPI marks districts it could not match to a P-code with codes like `MZ01-XXX`, and their province can be wrong (in October 2026 Mozambique's Quissanga was under Niassa and Nampula's districts under Sofala): they count in the totals but not in a province. Larger answers are read page by page (`hapiAll` in `hapi/api.ts`): HAPI stops at 10,000 rows without saying so.
- **Admin boundaries and choropleths**: provinces and districts come from OCHA's COD-AB as PMTiles on Source Cooperative (`https://data.source.coop/hdx/cod-ab/global/admin<1|2>/admin<1|2>.pmtiles`, 75 and 190 MB, zoom 0 to 11, 112 countries, CC BY 3.0 IGO). This replaces the sources plan-006 tried and dropped (COD-AB GeoParquet, World Bank levels 1 and 2, Overture divisions, geoBoundaries): MapLibre reads only the tiles in view by range request, through the `pmtiles` package's protocol, and every feature has `iso3`, `adm<N>_pcode` and `adm<N>_name`. HDX HAPI's areas come from the same CODs, so its rows join to the tiles by P-code (checked for Mozambique). Unlike other data layers, these are MapLibre layers, not deck.gl ones, so a choropleth sits under the basemap's labels (`apps/web/src/map/adminAreas.ts`): the tool returns what to draw (`geo.adminAreas`: level, country, values by P-code), and `syncAdminLayers` keeps the map's layers in step with the board and adds them again after a basemap change (`setStyle(…, { diff: false })` so `style.load` fires). `map.addBoundaries` (map plugin, tool `boundaries.codab`) draws outlines everywhere; `map.addChoropleth` (hapi plugin, tool `hapi.choropleth` in `hapi/choropleth.ts`) colors one country's areas by organizations present (with a sector), or political violence events or fatalities of the last 12 months, in five quantile classes with 0 apart, a legend in the layer list, and the value under the pointer while the map is edited. A map's "Add layer" menu offers the figures of the who's where and conflict widgets on the board, and fits the adder's view to the country with the geocoder. Rows HAPI could not place (`-XXX` codes) are left out and counted in the legend; an area with no HAPI row shows "no data", not 0. Country outlines still come from the World Bank layer: COD-AB has no level 0 file.
- **Uploads** (`packages/core/src/uploads.ts`, `apps/worker/src/uploads.ts`): files people upload to a board, in R2. `POST /uploads?room=<room>&name=<file name>` with the file as the body goes to that room's Durable Object, which stores it and appends an entry (id, `kind`, name, type, size, uploader, time) to the doc's `uploads` array, so the list syncs like any edit. Entries are written by the room, not by browsers, so a later client such as an MCP server gets its uploads listed too; like the chat, they are not board objects (no ops, no undo). `GET /uploads/<id>` is served by the Worker, with `nosniff`, `default-src 'none'` and an immutable cache, and `sandbox` for every type but PDF: a sandboxed document cannot load the browser's PDF viewer, which keeps a PDF's scripts away from the board's origin itself. The type is read from the file's first bytes (`UPLOAD_TYPES`): `media` is PNG, JPEG, GIF and WebP, at most 10 MB; `document` is PDF, at most 25 MB (`MAX_UPLOAD_BYTES`, also checked in the browser). GeoParquet is not accepted yet, and comes with the objects that show it. Never SVG or HTML: served from the board's origin, they could run scripts there. **Ready for accounts:** the R2 key is `uploads/<random uuid>` and says nothing about who uploaded it, so links do not change when accounts come; the uploader and room are custom metadata (`uploader`: the browser's person id, as the browser claims it until accounts exist; `room`), and access checks can be added to `GET /uploads/<id>` without changing links. Anyone with a deployed URL can upload, as anyone can edit its boards, and anyone with a file's link can see it. The `UPLOADS` binding has no `bucket_name`, so `wrangler deploy` makes a bucket per Worker (`<worker>-uploads`); `wrangler dev` keeps files in `.wrangler/`. Deleting a branch deletes its Worker but not its bucket.
- **Uploads gallery** (`apps/web/src/uploads/UploadsPanel.tsx`, the Uploads button at the top right): the board's uploads in Media and Documents tabs, newest first, whether or not they are still on the board. Any file can be put back on the board, in the middle of your view, as an image or a PDF object (`placeUpload` in `uploads/drop.ts`, which drops use too); every file has its link and an open button.
- **Image widget**: a picture someone uploaded (`images` plugin, `packages/plugins/src/images.ts`; UI in `apps/web/src/images/`). A new image opens the file chooser; double-click replaces the picture, or drop a file on it. The board stores only `imageId`, an upload's id; the header copies its link. Uploading and showing are separate: uploading is not an op (the file goes to the room, which answers an id); showing one is `image.add` or `image.setImage` with that id, so the agent, or a later client such as an MCP server, can place an image that was already uploaded.
- **PDF widget** (`pdfs` plugin, `packages/plugins/src/pdfs.ts`; UI in `apps/web/src/pdfs/`): a PDF someone uploaded, drawn with pdf.js (`pdfjs-dist`, its legacy build: the standard build uses JavaScript only the newest browsers have, such as `Map.prototype.getOrInsertComputed`, and drew nothing in Safari), which loads with its worker on the first PDF shown (`pdfs/pdf.ts`), so boards without PDFs do not download it; each file is loaded once per tab. The type stores `fileId` (an upload's id), `name` and `page`, the page its card shows for everyone. It has in-focus mode (double-click, F or the header's button): focus shows every page sharp at screen size, drawn as they come near the view, and the Options panel sets the card's page (`pdf.setPage`) on the draft, so others see it when it is shared; it also offers the page in view (`pdfs/live.ts`). There is no toolbar tool: PDFs come from drops and the gallery. The agent can place an uploaded PDF (`pdf.add` with `fileId`) and set its page.
- **Montandon needs a bearer token, which never reaches the browser.** The browser posts STAC search bodies to `/monty/search`; the Worker adds `MONTANDON_TOKEN` and forwards them to `MONTANDON_BASE_URL` (`apps/worker/src/monty.ts`, standard `fetch` only, so it can move to another server). The room's agent searches with the same token, without the proxy (`stacSearch`). The base URL is a var in `wrangler.jsonc`: the staging API, as `agent-docs/features.md` scopes. Without the token, `/monty/search` answers 503. Anyone with a deployed URL can run searches through the token, as anyone can edit its boards. `/tools/geocode` works the same way for OpenCage (`apps/worker/src/geocode.ts`): it passes only `q, limit, countrycode, bounds, language`, adds `OPENCAGE_API_KEY`, and masks the key in any answer. OpenCage's public test key `6d0e711d72d74daeb2b0bfd2a5cdfdba` always answers with one place in Münster: use it to check the wiring without a real key.
- **Rooms:** one board per `#room=<id>`. Opening the app without one, or pressing New board, starts a board with a random 16-character id (`board/room.ts`); the URL is the link to share. There is no access control: anyone with the link can edit, so keep real exercise data off the preview.

### Adding an object type

A type is a headless definition plus its UI. The canvas, toolbar, side panel, palette and agent read everything from the registries, so a new type needs no changes elsewhere.

1. In a plugin in `packages/plugins` (`definePlugin`), add an `ObjectTypeDef`: zod `fields`, `defaultSize`, `layer` (`top` for content, `bottom` for backgrounds), `summarize` for the agent, and `defaultColor` and `textSize` if the side panel can set them. It gets a `<type>.add` op. A field added later, when objects of that type already exist on boards, must be optional, with a default where it is read. Never change a stored type name or field.
2. In the web app, call `registerObjectUI` (`canvas/registry.ts`): a `View`, a `tool` (key, label, Phosphor icon), and the behaviour it needs: `editable` (double-click), `editOnCreate`, `widthOnly`, `isEmpty` (removed when left empty). Import the file from `apps/web/src/plugins.ts`; the order of registration is the toolbar order.
3. Write through ops only. Store references to data (an event id, a tool recipe), not the data itself: each browser fetches what it shows.

Older tabs show a placeholder for a type they do not know, so a board stays usable while people reload after a deploy.

The first prototype is on the `experiment` branch: a headless op runtime, typed data links, a disasters plugin on Montandon, and a natural-language command pipeline. It is a reference, not a base. Read it before rebuilding a part it covered, in particular:
- `apps/web/src/nodes/MapView.tsx` and `plans/plan-005.md`: maps inside a canvas (edit and focus modes, WebGL context limits, pixel ratio at canvas zoom).
- `packages/plugin-disasters/src/montyProvider.ts`: the Montandon queries that `packages/plugins/src/monty/client.ts` has not taken over yet: related events near an event and impact tables.
- `feat/tools-registry` (`plans/plan-006.md`): the measured sizes and timings behind the data tools, and the admin boundary sources that were tried and dropped (COD-AB, Overture divisions, geoBoundaries).

## Setup and commands

Node 22 or later.

```sh
npm install
echo 'MONTANDON_TOKEN=<token>' > apps/worker/.dev.vars   # once; git-ignored. Needed for event search
echo 'OPENROUTER_API_KEY=<key>' >> apps/worker/.dev.vars # needed for the board agent
echo 'OPENCAGE_API_KEY=<key>' >> apps/worker/.dev.vars   # needed for place search
echo "HAPI_APP_IDENTIFIER=$(printf 'humanitarian-ttx:<email>' | base64)" >> apps/worker/.dev.vars   # needed for country context
npm run sync        # Worker + Durable Objects locally (wrangler dev), http://localhost:8787
npm run dev         # web app with hot reload, http://localhost:5173 (proxies /connect, /monty, /tools, /notebooks, /reliefweb and /hapi to :8787)
npm run mcp         # MCP companion for your own Claude or Codex, http://127.0.0.1:8790/mcp (plans/plan-010.md)
npm test            # vitest
npm run typecheck
npm run build
npm run deploy      # build the web app and deploy the Worker (needs `npx wrangler login` once)
```

`npm run sync` also serves the last `npm run build` at :8787, the same way the deployed Worker does. Local room state is in `apps/worker/.wrangler/`.

## Deploys

GitHub Actions deploy every push to Cloudflare (`.github/workflows/deploy.yml`), after typecheck and tests pass:
- `main` deploys to the `humanitarian-ttx` Worker.
- Every other branch deploys to its own Worker, `humanitarian-ttx-<branch>` (naming rule in `.github/scripts/worker-name.sh`), with its own rooms. A branch that changes the board format cannot break `main`'s boards.
- Deleting a branch deletes its Worker and its rooms (`delete-branch-worker.yml`).
- The deployed URL is in each run's summary, and on the branch's pull request as one comment that each deploy updates (`.github/scripts/pr-preview-comment.sh`). A pull request opened after the branch deployed gets the link from `pr-preview-link.yml`.

Repository secrets: `CLOUDFLARE_API_TOKEN` (a token limited to editing Workers and R2, which deploys need to make each Worker's uploads bucket; R2 must be enabled on the account), `CLOUDFLARE_ACCOUNT_ID`, `MONTANDON_TOKEN`, `OPENROUTER_API_KEY`, `OPENCAGE_API_KEY` and `HAPI_APP_IDENTIFIER`. Cloudflare keeps secrets per Worker and each branch is its own Worker, so the workflow uploads the API keys the repository has with every deploy (`--secrets-file`). A missing key does not fail the deploy: event search, place search and country context answer 503, and the agent answers that it is not configured.

## Before editing

- Identify the requested outcome and how to verify it. For substantial or ambiguous work, state the scope and assumptions before implementing. Ask when uncertainty would change behavior or a shared contract; resolve routine implementation choices using existing conventions.
- Inspect the working tree and relevant code, tests, and callers. Search for an existing implementation before generating a new one.
- Treat existing uncommitted changes as another contributor's work. Preserve them, stage only your own changes, and ask before overwriting overlapping work. Re-read files before editing if they may have changed during the task.
- Keep independent tasks on separate branches or worktrees. Coordinate overlapping changes to shared interfaces, configuration, and lockfiles; do not silently broaden the task to accommodate another task's work.

## During code generation

Apply these rules while choosing an implementation and again when reviewing the diff:

- **YAGNI:** Implement the current requirement and its necessary correctness safeguards. Every new option, dependency, abstraction, and fallback must serve that requirement or an established contract. Defer speculative extension points, unused helpers, and features for hypothetical future callers.
- **DRY:** Keep each business rule and invariant in one authoritative place. Reuse existing code when its semantics match. Extract shared code when callers represent the same concept and should change together; similar syntax alone is not enough. Small duplication is preferable to coupling unrelated behavior through a configurable abstraction.
- **Simplicity:** Choose the smallest clear design that satisfies the requirement. Prefer explicit control flow and existing building blocks. Add indirection only when it reduces demonstrated complexity; avoid broad cleanup, renaming, or formatting outside the task.
- **Compatibility:** Inspect affected callers before changing shared interfaces or data formats. Preserve established behavior outside the requested change, and document intentional compatibility changes and any migration needed.
- **Maintainability:** Use names and boundaries that make intent clear to the next contributor. Comments should explain constraints or reasoning that the code cannot express. Record consequential shared design decisions in the repository rather than leaving them only in chat.
- New frameworks or dependencies require a plan, ADR, or ticket as well as the human approval described below.

## Verification and handoff

- Verify observable behavior against the requested outcome. Add or update tests for changed behavior and bug regressions; choose the test level that catches the failure without binding the test to implementation details. Test-first and implementation-first workflows are both acceptable.
- Run the relevant available tests, type checks, and linters before requesting review. For documentation-only changes, check accuracy, links, and the diff. Report checks that failed or could not run, including known pre-existing failures; never imply an unrun check passed.
- Review the final diff for scope, accidental changes, unnecessary abstractions, and duplicated rules. Account for every changed file before handing off.
- Summarize the resulting behavior, why it changed, verification performed, and any remaining limitations or follow-up work. Give reviewers enough context without requiring access to the agent conversation.

## Git and PRs

- Start new work from `main` on a task branch; continue an existing task on its branch. Integrate through a reviewed PR, subject to the publishing approval below; never push directly to `main`.
- Keep each PR focused on one coherent change. Separate unrelated cleanup so other contributors can review, merge, and revert changes independently.
- Write clear commit messages describing *why*, not just *what*.
- Resolve conflicts by preserving the intent of both changes and rerun affected checks. Ask when those intents conflict instead of choosing one contributor's version by default.

## Ask before

Agents should check with a human before:

- Adding or upgrading dependencies
- Changing scenario content or exercise logic in ways facilitators rely on
- Deleting files, rewriting history, or force-pushing
- Anything that publishes or sends data outside the repo
